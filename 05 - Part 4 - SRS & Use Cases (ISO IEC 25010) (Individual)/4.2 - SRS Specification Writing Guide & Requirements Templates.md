# 4.2 SRS Specification Writing Guide & Requirements Formulation

> [!IMPORTANT]
> **Coursework Deliverable**: Part 4.1 Software Requirements Specification (10 Marks — Individual).  
> **Coursework Directive**: *"write a brief document containing the description of two requirements as part of the SRS in your selected sub-topic [performance, security, portability, usability, maintainability] with the support of the ISO/IEC 25010 standard."*  
> **Engineering Standard**: Formulated according to **ISO/IEC/IEEE 29148:2018 (Requirements Engineering)** and RFC 2119 precision keywords.

---

## 📐 The SMART Requirement Specification Anatomy

Every requirement must contain these 6 essential dimensions:

```
┌────────────────────────────────────────────────────────────────────────────────────────┐
│ [ID] : Unique Requirement Identifier (e.g., SRS-PERF-01, SRS-SEC-01)                  │
│ [Sub-Characteristic] : Specific ISO/IEC 25010 sub-characteristic                      │
│ [Statement] : Formal normative declaration using "SHALL" / "MUST"                      │
│ [Verification Metric] : Quantifiable, testable acceptance threshold                    │
│ [Clinical / Operational Rationale] : Problem in MHE case study that this resolves      │
│ [Verification Method] : Inspection / Analysis / Test / Demonstration                   │
└────────────────────────────────────────────────────────────────────────────────────────┘
```

### TOPIC 1: Performance Efficiency (Member 1)

#### Requirement 1: Time Behaviour (Real-Time Emergency Triage Latency)
- **Requirement ID**: `SRS-PERF-01`
- **ISO/IEC 25010 Sub-Characteristic**: 4.2.1 Time Behaviour
- **Formal Statement**: The SATZ AI Predictive Triage Microservice **SHALL** process incoming patient symptom and vital telemetry payloads, calculate the Manchester Triage acuity score, and return an optimized ward bed reservation confirmation within a **response time of ≤ 250 milliseconds at the 99th percentile (p99)** under a sustained baseline load of 1,000 concurrent clinical requests.
- **Verification Metric**: Measured via automated k6 load testing scripts running 1,000 virtual users (VUs) for 30 minutes; mean response time must not exceed 120ms; max tail latency must not exceed 250ms.
- **Case Study Rationale**: Clinical emergencies in Greater Manchester mandate immediate decision-making. Delays in system response directly risk patient morbidity during acute cardiac or respiratory events.
- **Verification Method**: Test (Automated Performance Load Testing).

#### Requirement 2: Capacity (High-Throughput IoT Sensor Telemetry Ingestion)
- **Requirement ID**: `SRS-PERF-02`
- **ISO/IEC 25010 Sub-Characteristic**: 4.2.3 Capacity
- **Formal Statement**: The SATZ Telemetry Edge Ingestion Gateway **SHALL** sustain an ingestion capacity of **at least 10,000 concurrent MQTT sensor telemetry payloads per second** across hospital wards and facilities without dropping more than 0.001% of messages or exceeding 500ms end-to-end ingestion pipeline latency into TimescaleDB.
- **Verification Metric**: Measured via a distributed Locust cluster generating 10,000 MQTT packets/sec over TLS 1.3 for 60 continuous minutes; zero queue overflow exceptions allowed.
- **Case Study Rationale**: MHE uses diverse sensors and controllers across multiple facilities. If the ingestion bus bottlenecks, predictive maintenance models will fail to detect equipment anomalies before physical breakdown occurs.
- **Verification Method**: Test (Stress and Ingestion Capacity Testing).

### TOPIC 2: Security (Member 2)

#### Requirement 1: Confidentiality & Role-Based Access Control (RBAC)
- **Requirement ID**: `SRS-SEC-01`
- **ISO/IEC 25010 Sub-Characteristic**: 4.3.1 Confidentiality
- **Formal Statement**: The system **SHALL** enforce field-level cryptographic tokenization (AES-256 GCM) on all Electronic Patient Records (EPR) and Special Category data such that third-party service providers (maintenance technicians and private ambulance drivers) are strictly restricted from accessing patient clinical diagnoses or unmasked NHS numbers.
- **Verification Metric**: 100% of API endpoints accessed via Provider OAuth2 JWT tokens must redact diagnostic fields; verified through automated security fuzzing and penetration tests.
- **Case Study Rationale**: MHE currently handles third-party providers via disjointed communication. Restricting provider views guarantees compliance with UK GDPR Article 9 and Caldicott Principle 2 (Data Minimization).
- **Verification Method**: Test & Analysis (SAST security analysis and automated API penetration testing).

#### Requirement 2: Integrity & Authenticity (Cryptographic Sensor Telemetry Signing)
- **Requirement ID**: `SRS-SEC-02`
- **ISO/IEC 25010 Sub-Characteristic**: 4.3.2 Integrity & 4.3.5 Authenticity
- **Formal Statement**: Every IoT facility controller and biomedical sensor packet transmitted to the edge gateway **SHALL** contain an HMAC-SHA256 signature generated using a hardware-secured private key (TPM 2.0 / Secure Element), and the gateway **SHALL** reject and log any payload where the signature verification fails.
- **Verification Metric**: Injected spoofed or modified telemetry packets must achieve a 100% rejection rate with security alert emission within < 50ms.
- **Case Study Rationale**: Attackers or rogue controllers could inject fraudulent telemetry (e.g., false normal temperature on a overheating autoclave), masking physical facility collapse.
- **Verification Method**: Test (Negative Security Penetration Testing).

### TOPIC 3: Usability (Member 3)

#### Requirement 1: Learnability & Error Protection (Clinical Triage Guidance)
- **Requirement ID**: `SRS-USAB-01`
- **ISO/IEC 25010 Sub-Characteristic**: 4.4.2 Learnability & 4.4.4 User Error Protection
- **Formal Statement**: The Clinical Triage workstation interface **SHALL** provide contextual inline guidance and automated input validation such that a newly onboarded clinical staff member can complete an emergency bed dispatch within **≤ 3 minutes of first system use without external training**, with 0% occurrence of fatal physiological data entry errors (e.g., heart rate > 300 bpm).
- **Verification Metric**: Evaluated via formal usability lab testing with 10 clinical staff (System Usability Scale - SUS score ≥ 80; task completion rate 100%).
- **Case Study Rationale**: The case study highlights that *"limited training is provided to staff"*. An intuitive, error-preventing interface neutralizes this institutional deficit.
- **Verification Method**: Demonstration (Clinical Usability Testing).

#### Requirement 2: Accessibility (WCAG 2.1 AA Patient Self-Service Portal)
- **Requirement ID**: `SRS-USAB-02`
- **ISO/IEC 25010 Sub-Characteristic**: 4.4.6 Accessibility
- **Formal Statement**: The Patient Self-Service web and mobile portal **SHALL** comply 100% with the **W3C Web Content Accessibility Guidelines (WCAG) 2.1 Level AA**, featuring full keyboard navigation, screen reader compatibility (ARIA labels), dynamic text re-sizing up to 200%, and multi-language support (English, Urdu, Polish, Arabic).
- **Verification Metric**: 100% pass score on automated accessibility engines (Axe DevTools / Pa11y) plus manual assistive technology audit with zero critical accessibility violations.
- **Case Study Rationale**: Patients across Manchester struggle to access services due to inadequate digital accessibility and language barriers.
- **Verification Method**: Inspection & Test (Automated WCAG Audit and Assistive Tech Testing).

### TOPIC 4: Portability (Member 4)

#### Requirement 1: Adaptability (Cross-Platform Responsive Mobile & Tablet Operation)
- **Requirement ID**: `SRS-PORT-01`
- **ISO/IEC 25010 Sub-Characteristic**: 4.5.1 Adaptability
- **Formal Statement**: The SATZ Clinical Operations application **SHALL** adapt dynamically to screen resolutions ranging from 375x667 pixels (mobile smartphones) to 1920x1080 pixels (hospital workstations) across iOS, Android, and Chromium-based browsers without loss of functionality or horizontal scroll degradation.
- **Verification Metric**: Validated across BrowserStack matrix of top 10 NHS-utilized hardware devices with 0 layout breakage issues.
- **Verification Method**: Test (Cross-Platform Automated UI Testing).

#### Requirement 2: Replaceability & Installability (Containerized Multi-Cloud Deployment)
- **Requirement ID**: `SRS-PORT-02`
- **ISO/IEC 25010 Sub-Characteristic**: 4.5.2 Installability & 4.5.3 Replaceability
- **Formal Statement**: All SATZ microservices **SHALL** be packaged as OCI-compliant container images deployable via standard Kubernetes Helm charts, capable of completing automated cold installation in a new UK cloud region in **≤ 15 minutes**.
- **Verification Metric**: Automated CI deployment pipeline execution timed and verified in isolated Azure/AWS environments.
- **Verification Method**: Test (Automated Infrastructure-as-Code Deployment Drills).

### TOPIC 5: Maintainability (Member 5)

#### Requirement 1: Modularity & Loose Coupling (Independent Microservice Lifecycles)
- **Requirement ID**: `SRS-MAINT-01`
- **ISO/IEC 25010 Sub-Characteristic**: 4.6.1 Modularity
- **Formal Statement**: The Reward Scheme Service and Facility Maintenance Service **SHALL** operate as decoupled microservices communicating strictly via asynchronous Kafka event contracts, such that modifying or deploying a new release of the Reward Service causes **zero downtime or code changes** in clinical triage microservices.
- **Verification Metric**: Independent Canary deployment executing during live simulated triage traffic with 0 dropped triage transactions.
- **Verification Method**: Demonstration (Canary Deployment Drill).

#### Requirement 2: Analyzability & Testability (Distributed Tracing & Automated Coverage)
- **Requirement ID**: `SRS-MAINT-02`
- **ISO/IEC 25010 Sub-Characteristic**: 4.6.2 Analyzability & 4.6.4 Testability
- **Formal Statement**: Every microservice **SHALL** inject OpenTelemetry correlation IDs into all incoming requests, and maintain automated unit and integration test coverage of **≥ 85% line coverage**, failing CI builds if coverage drops below this threshold.
- **Verification Metric**: SonarQube automated code quality gate validation on every pull request.
- **Verification Method**: Inspection (Automated SonarQube CI Quality Gate).
